# Cross-File Consistency Audit

## (1) Protocol/Version Consistency
*   **Version Mismatch**: `ember-net` defines `PROTOCOL_VERSION: u16 = 2` (`crates/ember-net/src/lib.rs`), while `pong-core` defines `PROTO_VERSION: u16 = 7` (`crates/pong-core/src/lib.rs`). The `pong-server` enforces version checks against `PROTO_VERSION` (7) but `ember-net`/`game` do not enforce a version with `pong-server` (which uses a different crate).
*   **TICK_HZ Inconsistency**: `ember-net` defines `TICK_HZ: u32 = 60` (`crates/ember-net/src/lib.rs`), matching the arena shooter's simulation tick rate in `pong-core` (`crates/pong-core/src/shooter.rs`), but the Pong crate (`crates/pong-core/src/sim.rs`) also uses `FIXED_DT: f32 = 1.0 / 60.0`, implying a 60Hz tick. This is consistent but conflates two distinct game modes (Pong vs. Shooter) under the same constant namespace.

## (2) Layering Violations
*   **Renderer Accessing Platform Types**: In `crates/ember-engine/src/renderer.rs`, the struct `Renderer` holds a `wgpu::Surface<'static>` (platform type) and `wgpu::Device`. This violates the top-down dependency rule (`game -> sim -> renderer -> platform`) because `Renderer` is the "sim" layer in this architecture but holds the platform-specific `wgpu` types directly. The `app.rs` file correctly passes the `Window` and `EventLoop` down to `Renderer::new`, but `Renderer` itself is defined in the "sim" crate.
*   **Game Accessing Platform Inputs**: The `EmberGame` trait in `crates/ember-engine/src/lib.rs` requires `update(&mut self, input: &InputState, dt: f32) -> Frame`. The `game` crate (`crates/game/src/main.rs`) implements this trait and accesses `winit::event::KeyCode` and `winit::event::MouseButton` directly in the implementation, bypassing the abstraction layer.

## (3) Duplicated Logic
*   **Asset Loading**: `crates/game/src/main.rs` contains a function `load_monument()` that calls `ember_engine::assets::load_glb` and `load_texture()`. `crates/game/src/main.rs` also contains `plane_mesh` and `box_mesh` that manually construct `MeshData`. `crates/pong/src/lib.rs` contains `push_gun` and `push_parts` which manually construct `Instance` objects, while `crates/game/src/character.rs` contains `push_character` with similar logic. The logic for creating meshes from primitives is duplicated in `game` and `pong`.
*   **Camera Construction**: `crates/game/src/main.rs` constructs a `Camera` for rendering in `arena_frame`. `crates/pong/src/lib.rs` constructs a `Camera` in `build_scene`. The logic for setting `eye`, `target`, and `fov_y_deg` is duplicated.

## (4) Dead/Orphaned Public Items
*   **Unused Constants**: `crates/ember-net/src/lib.rs` defines `MAX_FRAME_BYTES`, `MAX_NAME_LEN`, `CLIENT_TIMEOUT_SECS`, `MOVE_SPEED`, and `ARENA_HALF`. `crates/pong-core/src/` defines similar constants for the arena shooter (`ARENA_HALF`, `MOVE_SPEED`, `MAX_HP`, `RELOAD_SECS`, etc.) and for Pong (`COURT_HALF_W`, `COURT_END_Z`, etc.). `ember-net` defines constants that are only used by the `game` crate (via `ember_net` re-exports), but the `pong` and `pong-core` crates do not use `ember-net`, creating orphaned definitions that are not shared.
*   **Unused Structs**: In `crates/pong/src/lib.rs`, `SceneParams` is used internally by `build_scene` but is not re-exported or used by any other module. `PrevState` is used internally by `LocalGame` but is not exported.

## (5) Riskiest Cross-File Assumptions
*   **Arena Half Consistency**: `crates/pong-core/src/shooter.rs` and `crates/pong-core/src/sim.rs` define `ARENA_HALF`. `crates/pong-core/src/` defines `ARENA_HALF: f32 = 24.0`. `crates/game/src/main.rs` uses `ember_net::ARENA_HALF` (which is 20.0) to clamp the offline player position, but the `pong-core` shooter simulation runs in an arena of size 48.0 (half = 24.0). If a player connects to a shooter server from the `game` crate using the offline arena size (20.0), they will be able to walk outside the server's arena bounds.
*   **Tick Rate**: `crates/ember-net/src/lib.rs` defines `TICK_HZ: u32 = 60`. `crates/game/src/world.rs` uses `TICK_HZ` to calculate interpolation steps (`step = dt * TICK_HZ as f32`). `crates/pong-core/src/shooter.rs` simulates at 60Hz, but `crates/pong-core/src/sim.rs` (Pong) also simulates at 60Hz. However, the `pong` crate's online client in `online.rs` uses `pong_core::proto::STATE_EVERY_TICKS` (2) to interpolate, not the `TICK_HZ` constant from `pong_core::shooter`. There is no single source of truth for tick rate across the two distinct game modes in `pong-core`.

# Health Verdict

The workspace demonstrates a **moderate** architectural health. The separation of concerns between `ember-engine` (platform/renderer), `game` (client logic), and `pong-core` (shared sim/protocol) is generally well-implemented. The `pong-core` crate successfully isolates the deterministic simulation from the engine. However, the architecture is fractured by the lack of a unified protocol standard; `ember-net` and `pong-core` are effectively parallel worlds with different constants and versions. This leads to potential gameplay inconsistencies (e.g., offline arena size vs. server size) and duplicated code for asset handling and mesh generation. The layering rule is mostly respected, though the Renderer holding `wgpu` types technically violates the strict abstraction intended by the "sim" layer.
