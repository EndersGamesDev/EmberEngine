## Architecture (from the v7 re-framing)

- The scene and present command buffers reach the queue in one `submit` call (`crates/ember-engine/src/renderer.rs:798-799`) under a comment claiming the ATW sliced-submission rule (`crates/ember-engine/src/renderer.rs:673-675`). Splitting the call is a one-line fix worth making for the stage boundary, but it does **not** deliver sliced scheduling — on one in-order queue the present still runs behind the scene work either way, and real slicing needs the scene emitted as several separately submitted chunks (roadmap step 7). Fix the comment along with the code (`docs/presenter-architecture.md` §5).
- Shader hot-reload rebuilds both the scene and the present pipeline from one clock (`crates/ember-engine/src/renderer.rs:807-835`) and needs re-homing before the presenter split can be written (`docs/presenter-architecture.md` §8.1).
- The scene-Hz throttle lives inside the renderer, so the renderer decides whether the renderer runs (`crates/ember-engine/src/renderer.rs:608-612`); the clock belongs above both GPU stages (`docs/presenter-architecture.md` §8.2).
- `cursor_ndc()` and `aspect()` have no callers anywhere in the workspace, and the shooter's head comment claiming cursor unprojection (`crates/arena/src/online.rs:2`) is stale — it aims with relative deltas. The API is worth keeping; nobody should assume a shipped game is exercising it (`docs/input-latch.md` §7).
- Pointer capture fires on any mouse press with no button filter (`crates/ember-engine/src/app.rs:195-203`), so in the one game that opts in the fire button is also the capture gesture; and `cursor_ndc` goes stale rather than `None` under pointer lock (`docs/input-latch.md` §7).
- `docs/state-model.md` names the five levels of state the engine holds (abstract scene, sent/received network, local, rendered, presented) and is the conceptual root above the other architecture documents; its open items are whether level 1 gets a checkable artefact at all (no schema exists — the scene concept is hand-written three times, in the sim structs, the protocol enums and the instance builder) and whether the arena client's prediction gets a fixed-step accumulator rather than integrating on the render clock (`crates/arena/src/online.rs:731-740`).
- Weak-device performance is assessed in `docs/weak-device-performance.md`, which owns the prioritized levers and the measurement items: backface culling is off (`crates/ember-engine/src/renderer.rs:963`), `scene_scale` is pinned at 1.0 against an uncapped device-pixel-ratio backing store (`crates/ember-engine/src/app.rs:233-234`), scene depth is stored every frame and read by nothing (`crates/ember-engine/src/renderer.rs:701-704`), the ATW rig is compiled out on the only target that is actually weak (`crates/ember-engine/src/renderer.rs:611-612`), and the workspace defines no `[profile.release]` for the wasm payload.

## The residual join failure — what has been ELIMINATED (2026-08-31)

- Roughly 1 run in 45-60 of `two_clients_see_each_other_move` still loses a single message after the connection is established. It surfaces as whichever message was next — `PlayerJoined`, `Phase`, `Joined`, or `Welcome` — so it looks like four different bugs and is one. Do not re-diagnose it from the symptom.
- EVERY application-level drop path is now instrumented and has been observed SILENT across ~250 runs while the loss still occurred: the server's frame parse (`undecodable frame`), its hub-channel send, `handle_event`'s unregistered-connection branch, the per-drain rate limiter, `version_ok`'s refusal, `send_to`'s queue-full and connection-gone arms, and the client reader's undecodable-frame and thread-death paths. `hello conn=N proto=1` is logged for both peers on every failing run, so the connection is fully established before the loss. The loss is therefore BELOW the application layer.
- The untested hypothesis is the 5 ms `SO_RCVTIMEO` on both read loops interacting with tungstenite's framing — the same family as os error 997, which was proved. Testing it means lengthening the timeout, which costs outbound latency (up to one tick of the 30 Hz broadcast), so it is a tradeoff rather than a free fix and was not taken unilaterally. The clean answer is async I/O (tokio-tungstenite), where no timeout is needed at all.
- Blast radius, and the reason this did not block shipping v2: Windows-only and tungstenite-only. Browser clients use `web_sys::WebSocket` with no read timeout; the deployed server is Linux, where the timeout is a handled `EAGAIN`. It affects native Windows clients and Windows-side tooling, INCLUDING the deploy probe — retry a failed probe once before concluding a host is broken.
- Measurement note: `cargo test --workspace` STOPS at the first failing test binary, so a tripped flake yields a short run (e.g. suites=10 passed=135) that reads like a mass regression. Use `--no-fail-fast`, and always report the suite count: 31 means complete, fewer means truncated.

## Reboot durability is blocked by SELinux, not by a missing env var (2026-09-01)

- `systemctl --user start|restart|stop|is-active` returns **Access denied** on specht from a non-interactive ssh session, for BOTH accounts. Measured directly, not inferred: as `end` (uid 1008, `Linger=yes`, `/run/user/1008/bus` present) a throwaway unit could be written and `enable`d — the symlink was created — but `start` was refused. Setting `XDG_RUNTIME_DIR` and `DBUS_SESSION_BUS_ADDRESS` changes nothing; the peer session saw the same as `ender`.
- The split is read-vs-write, not env-vs-no-env: `is-system-running`, `show`, `list-units` and `is-enabled` all succeed, while every state-changing verb is denied. `getenforce` is **Enforcing**. This is the same SELinux policy that already denies several ports on this box (see the port note in deploy-pong-online.sh). So the units the watchdog installs cannot be controlled over ssh, and reboot durability via `systemd --user` is unavailable until either the policy is adjusted or the services move to system-level units with a sudo rule.
- Consequence already fixed in the deploy scripts: `is-enabled` is NOT a sound test for "systemd owns this". It reads a symlink and succeeds precisely where control fails, so predicting from it takes the systemd path and then dies on the restart. Both scripts now ATTEMPT the restart and fall back to `pkill`+`nohup` when it is refused.
- Until this is resolved, both games run under bare `nohup` and a reboot takes them offline exactly as before. The off-host `watchdog.sh` is the only thing standing between a reboot and a manual redeploy.

- `host.sh`'s header comment claims it needs `curl`; nothing in it, or in `host-name.sh` or `publish-host.sh`, invokes curl. Harmless but it sends someone installing a package they do not need — fix the comment. (`deploy-pong-online.sh`'s header has the same class of drift: it says the server binds `127.0.0.1:7778` while `PORT=7780`.)
- `publish-host.sh` enters MIRROR mode on any `--file` whose basename is not `server.json`, not just `host.json`, so a typo'd `--file serve.json` silently writes a one-entry mirror file instead of a book. Cheap guard: accept `host.json` explicitly and reject the rest.
- The legacy top-level address key for a game is recomputed only when the book carries that game's top-level PROTOCOL key, so a new game's `<id>_ws` is never re-pointed until `deploy-pages.sh` has written its `<id>_proto` at least once. Correct as designed, but it means the first deploy of a new game must ship a pages deploy too or its legacy key goes stale forever.
