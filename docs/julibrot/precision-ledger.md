# Julibrot precision ledger

## Scope and decision rule

This ledger follows the implemented path from a DOM input sample to an `Rgba8Unorm` surface pixel. A calculation earns precision only when reducing it can move the selected slice, move a feature on screen, change an escape decision or palette code, expose stale data, or defeat a replay or peer-agreement requirement that is actually in scope. Stable layouts, counters, generations, and bounds remain exact because an error selects the wrong data rather than a nearby colour. Arithmetic whose only defense is that it is currently tested exactly is marked "no reason found."

The arithmetic labels below are: `I`, exact checked integer or byte arithmetic and deterministic across CPU, GPU, machine, and word size once bytes are fixed; `B`, Astro-float with explicit ties-to-even rounding, intended to be cross-machine after `rounded_astro_precision` but not tested on wasm32; `F64`, IEEE binary64, with basic operations normally reproducible at a fixed operation sequence but `sin_cos`, `exp2`, `log2`, `log10`, `hypot`, and library implementation not promised bit-identical across machines; `F32-C`, CPU binary32 in a written operation order; `F32-G`, WGSL binary32, not promised bit-identical across GPU vendors or to `F32-C`; and `R`, rasterization, derivatives, filtering, and normalized-target conversion, which are picture operations rather than deterministic arithmetic. Astro-float's internal `Word` is `u64` natively and `u32` on wasm32; the wrapper rounds every requested width to a multiple of 64, but the repository has no wasm32-wasip1 parity test.

## Accuracy units and derivations

### Pixel-coordinate budget

For zoom `q` and width `W`, one plane pixel is `p = 4 / (2^q W)`, so the quarter-pixel coordinate budget used by the existing warp test is `p/4 = 1/(2^q W)`. At the edge of a 960-pixel grid, a relative scale error or basis-coefficient error moves a sample by at most about `480 error` pixels; keeping that below `0.25` needs error at most `1/1920 = 5.208e-4`. Binary32 unit roundoff is `u = 2^-24 = 5.960e-8`, about 8,700 times tighter before accumulated recurrence error. Around a unit-size absolute centre, half a binary32 ulp is `5.960e-8`; at `q=14`, `p=2.543e-7`, so the final absolute-coordinate rounding is about `0.234` pixel, while at `q=15` it is about `0.469` pixel. This derives the shallow/deep transition to within one zoom step and shows that bit identity is not its purpose.

The largest initial perturbation at the corner of a square plane is at most `2 sqrt(2) 2^-q`; it is `1.726e-4` at `q=14`. A mantissa rounded to binary32 therefore contributes far below a quarter pixel at the start. The exponent must remain integer-exact because an error of one changes scale by a factor of two and selects the wrong slice.

### Iteration and palette budget

The three palettes map smooth iteration `s` through a triangular hue with maximum channel slope `6 mix / period`. One `Rgba8Unorm` code value therefore permits `abs(delta s) <= period/(6*255*mix)`: `0.05363` iteration for Classic, `0.03565` for Ember, and `0.07262` for Ice. The picture-wide Final contract uses the strictest value, `0.03565` iteration. The current `1e-4` shallow and `2e-3` perturbation smooth tolerances are respectively 356 and 17.8 times stricter than the most demanding palette can display. Escape class and integer escape index remain exact outside a declared numerical boundary envelope because changing either can replace interior colour with exterior colour or jump roughly one iteration, many palette codes.

Height is `4 clamp(s/max_iter,0,1)-2`; the same `0.03565` iteration budget moves height by at most `0.1426/max_iter`, or `3.48e-5` at cap 4,096, below any visible mesh displacement at this grid. Lighting finally multiplies colour by a factor in `[0.58,0.82]`; requiring its final normalized channel to differ by at most one code value is sufficient, while matching derivatives or normals bit for bit is not.

### Reference-orbit error bound

Let exact reference sample `Z_r` be narrowed to one binary32 word per coordinate, let the stored value be `Zs_r`, and let `R_r = abs(Zs_r-Z_r)`, bounded componentwise by half an ulp of the stored word. Let exact and computed perturbations be `delta_n` and `dh_n`, with `D_n = abs(dh_n-delta_n)`, current scale-split centre-offset error `C`, and binary32 arithmetic/subnormal allowance `eta_n`. On a non-rebase advance, direct subtraction gives `D_(n+1) <= 2(abs(Z_r)+abs(delta_n))D_n + D_n^2 + 2 R_r(abs(delta_n)+D_n) + C + eta_n`; the displayed state additionally includes reference residual, carried perturbation error, its binary32 addition, and scaled subnormal allowance. This is the bound evaluated with the actual orbit and pixel.

A rebase does not erase error. The implementation sets the new perturbation from the already rounded `zh_n-Zh_0`, so immediately after rebase `D_n(rebased) <= E_n + R_0 + eta_rebase`; it then restarts at reference index zero. The predicate keeps a non-rebased perturbation no larger than the displayed state, but neither it nor the power-of-two renormalization recovers lost bits. Renormalization is exact only for values that remain normal and representable; the intervening binary32 multiplications and a subnormal result still require an allowance.

The PL-05 native split measurement now uses the reference recurrence itself: both Mandelbrot and Julia presets at zooms 14, 40, 80, and 256, caps 512 and 4,096. Across 16 named fixtures, 20,464 bounded orbit records and 40,928 coordinates with `|Z|≤16`, it found zero cases where `fl32(hi+lo) != hi`; one terminal escape record per Julia fixture was identified and excluded rather than pretending it met the bound. The earlier 16/10,000 result came only from non-orbit-shaped extreme exponents. The one-word premise holds on the production envelope, so WGSL and its CPU mirror consume `(re,im)`, and the repaired math envelope starts with the half-ulp binary32 reference error and scale-split centre error, bounds the binary32 operations, charges subnormal renormalization, and carries display error plus `R_0` and rebase rounding through every rebase.

A deliberately pessimistic global bound shows why an a-posteriori per-pixel bound is required. Before escape, take `abs(z) <= 16`, non-rebase `abs(delta) <= abs(z)`, `R = sqrt(2) 2^-20 = 1.349e-6`, binary32 spacing epsilon `epsilon = 2^-23`, and the existing envelope's form `eta = 32 epsilon (1+16)^2 = 1.102e-3`; then `E_(n+1) = 32 E_n + E_n^2 + R + eta` from `E_0=R` gives `E_1=0.001147`, `E_2=0.03781`, and `E_3=1.212`. Converting through the smooth derivative at radius 16 gives `3.73e-5`, `0.001230`, and `0.03943` iteration. The strict palette budget is crossed on the third advance, hence for every deep zoom `q>=14` at any cap at least 4; zoom cannot rescue this global worst case. It does not say typical pixels are wrong. It says the current global argument proves nothing through even Preview, and Final acceptance must use actual `R_r`, magnitudes, rebases, and margins or an exact-path image oracle.

The bignum reference is consequently necessary until both consumed coordinate words and escape decisions are stable enough for the picture. Absolute binary64 centre coordinates cease to resolve a quarter pixel around `q=43..45` at width 960, so an all-binary64 deep reference would eventually choose the wrong slice. Fast mode keeps the bignum centre, renders Preview from the first working-precision orbit, and defers the higher-precision consumed-word check to Final or Measure.

## Cost basis

The `docs/julibrot/math.md` performance section records one old warmed single-orbit Astro-float probe: at 100 decimal digits, 10,000 and 100,000 iterations took `7.530` and `73.125` ms; at 300 digits they took `19.516` and `229.887` ms. The current builder advances primary and `D+16` verification together, so linear scaling estimates a non-escaping cap-4,096 reference at roughly `6.2` ms near 100 digits and `16.0` ms near 300 digits before restart, transfer, or admission delay. Actual worker `compute_us` is the authoritative browser number, but no trustworthy capture is committed.

On sokol, the five native suites passed after 31.64 s compilation and finished in a 36.3 s run-report wall. A warmed 10,000-edit 1,024-bit navigation test took 3.92 s, or `0.392` ms per edit including owner/test overhead. A warmed tumbled test executed 1,536 plans, each including the 9x9x5 corpus, in 0.13 s, or about `0.085` ms per plan including assertions. The warmed synthetic drift test took 0.06 s and is not a frame cost.

There is no Julibrot benchmark target and no valid GPU timing ledger. The Julibrot facts finding in `docs/plans/backlog.md` records both scene and warp walls as exactly 2,000 ms with two polls, which is indistinguishable from a measurement cap and is not used as throughput. To make all frame estimates explicit rather than invented, this ledger uses a normalization of one billion executed pixel-iterations per second and 10 GB/s for the required SCRATCH-to-DATA copy; actual milliseconds scale as `1e9/R_iter` and `10GB/s/B_copy`. At 960x540 and cap 4,096 this gives Preview `2.0736` M iterations plus `0.5184` MB copy = `2.125` ms, Interactive `33.1776` M plus `2.0736` MB = `33.385` ms, and Final `2,123.3664` M plus `8.2944` MB = `2,124.196` ms. These are planning estimates, not populated overlay facts.

## Fast mode

### Single switch

The single public switch is `PrecisionMode::PictureFast`, paired with the retained `PrecisionMode::Deterministic`. It is a policy input, not a new view mode. It must appear in facts and captures so an image never silently claims deterministic provenance.

### Row-by-row behavior

`PictureFast` keeps exact integer layouts, lengths, grid indices, generations, stale gates, ownership, exponent fields, and terminal record categories because an error in them selects the wrong data rather than a nearby value. It keeps the bignum centre once a binary64 centre cannot meet `p/4`, but chooses its width from zoom, extent, edit history, and the Final plan rather than fixing 1,024 bits. CSS, gesture, plane, scale mantissa, warp, palette, height, lighting, and presented-pixel arithmetic may use local CPU or GPU `f32` and need not agree across machines.

Below `q=14`, fast mode accepts the current centre revision without requesting an orbit, because every refinement level selects the shallow kernel and consumes no reference record. For a deep edit, fast mode computes one working-precision reference first and immediately renders Preview at `ceil(W/8)` by `ceil(H/8)`, cap 32. It carries the current reference error and centre-offset information into the perturbation bound. Final either verifies only the GPU-consumed reference words against a higher-precision/interval result or escalates until the bound can certify the required corpus; it does not demand agreement of unused low words. Absolute binary64 reference generation is allowed only while its centre error is below `p/4`. Interactive is omitted. Every warped-surface refresh runs the 405-point tumbled error corpus because the result gates whether the warp may be displayed.

The reference therefore does not have to be mathematically exact. It does have to be accurate enough that its independently rounded samples, recurrence error, and every rebase remain inside the Final class/index/palette margins. A bignum centre remains necessary at deep zoom, and some adaptive reference verification remains necessary because the global bound fails at cap 4; computing two hundreds-of-bit orbits and comparing four words by two ulps is not necessary merely because perturbation is relative to a reference.

### Accuracy contract

For every pixel in the required Final corpus spanning the zoom-14 boundary, zooms 40, 80, 100, 256, 512 and the highest admitted precision plan, caps 64, 256, 512 and 4,096, all named planes, palette IDs, forced upward/downward rescale, nonzero and repeated rebases, and boundary fixtures: `PictureFast` must produce the same terminal class and escape index as `Deterministic` whenever the repaired propagated margin says the sample is outside its uncertainty envelope; valid escaped colour after palette and lighting must differ by at most one `Rgba8Unorm` code in each channel; interior, clear, and debug categories and alpha must match exactly; warp source coordinates must differ by at most 0.25 pixel. Preview and Interactive have no image-error guarantee, but must remain finite, generation-current, in bounds, and honest about glitches. Any failed Final pixel triggers precision escalation or rejects the fast result rather than relabeling it accurate.

### Test policy

Unconditional tests remain: checked layouts and indices; generation, stale, ownership, and prefix laws; shallow/deep boundary accuracy; exact terminal categories; repaired per-pixel perturbation envelope; exact class/index outside that envelope; Final end-to-end colour within one code; quarter-pixel navigation and warp; no invalid sample/pole; and all accuracy oracles against `Deterministic`. The existing `1e-9` inverse identity may be replaced by the quarter-pixel oracle, and `1e-4`/`2e-3` smooth limits may be relaxed only up to `0.03565` in fast mode.

Conditional on `Deterministic` or conformance mode are bit-exact CPU-mirror operation-sequence assertions, exact rebase-count agreement when the picture agrees, dyadic decode round-trips, identical delivered widths across Astro-float word sizes, exact two-word `D` versus `D+16` comparisons, synthetic drift identity, exact palette-oracle words, and exact planner residual words. Canonical byte validation and semantic decode bounds remain unconditional even though exact round-trip identity is conditional.

### Expected savings by refinement level

At the explicit one-billion-iterations/s and 10-GB/s normalization, current Preview costs `2.125` ms of GPU work after `6.2-16.0` ms of paired reference work and about `0.392` ms navigation, for `8.7-18.5` ms before small presentation costs. Deep fast Preview costs about `0.274` ms for 120x68 at cap 32 plus one `3.1-8.0` ms reference and reduced navigation, about `3.4-8.4` ms; time to first new picture saves approximately `5.3-10.1` ms, or 57-61%, before any credit wait. Shallow fast Preview needs no orbit and costs about `0.3-0.5` ms including navigation, saving `8.2-18.2` ms, or roughly 94-98%. Disabling fast-mode admission shaping for an explicit requested deep frame can additionally remove up to 1,000 ms of wait without reducing compute, while the shallow bypass removes that wait structurally.

Current Interactive costs about `33.385` ms and is then entirely superseded; fast mode omits it, saving `33.385` ms, 100% of that level. Current Final costs about `2,124.196` ms at cap 4,096. A deep fast Final that performs the deferred second orbit costs about `2,127.2-2,132.1` ms after the `0.06-0.08` ms planner saving, an incremental cost of `3.0-7.9` ms at that level; this is work moved out of Preview, not added to the full ladder. If a rigorous bound carried by the first orbit already certifies Final, Final instead saves only the planner `0.06-0.08` ms. A shallow Final needs no reference and likewise saves `0.06-0.08` ms. Lowering the Final cap or sampling fewer pixels cannot satisfy the stated contract in general.

Across a deep max-cap ladder that does require the deferred second orbit, normalized work falls by about `35.5-35.7` ms, roughly 1.6%; at the default cap 512, whose Final cost including copy is `266.250` ms and whose drafts are 11.72% of iteration work, it falls by about 11-12%. The shallow bypass adds the whole `6.2-16.0` ms paired-orbit saving, making the max-cap ladder saving about `41.7-51.7` ms, or 1.9-2.4%. A deep first orbit that certifies Final without a second orbit also adds `3.1-8.0` ms saving, but that is conditional upside rather than the baseline estimate. Actual early escape can make reference and discarded drafts a much larger share, so browser measurements must replace these normalized estimates.

Preview and Interactive are each 100% discarded as images when their successor lands; measured as shares of max-cap worst-case iteration work, they are 0.0961% and 1.5370%, with 1.6330% discarded together. Final is retained until a later edit, so its scheduled discard share is zero. Those percentages describe work, not latency value: Preview may still be worth its small cost because it is the only feedback before a two-second normalized Final.

## Calculations with no reason found for determinism

- CSS/grid conversion, anchor arithmetic, drag arithmetic, and `zoom_log2` accumulation: GPU `f32` would look like the same gesture with at most sub-quarter-pixel motion noise; CSS and event streams already prevent cross-machine replay without recording inputs.
- Plane `sin_cos`, final narrowing, and the `8*f32::EPSILON` postcondition: GPU `f32` would look unchanged while the basis remains within the derived `5.208e-4` edge-motion budget; the current refusal is about 546 times tighter than the picture requires.
- Fixed 1,024-bit centre precision at every zoom: an all-GPU `f32` centre would look normal only through the shallow range and then freeze or jump near zoom 15 and is therefore rejected; zoom-derived bignum width, rather than fixed maximal width, is the fast answer.
- Exact binary64 centre mirror and overlay depth digits: GPU `f32` would only change displayed last digits; neither value may place a deep pixel.
- The exact decimal formula and cross-machine boundary result of `precision_for`: GPU `f32` planning could choose a nearby starting width and the picture would be unchanged if adaptive Final certification passes; a fixed formula is useful provenance, not picture accuracy.
- Exact decode round-trip width and worker reconstruction of that planner formula: GPU `f32` planning would occasionally choose a neighboring starting width, but canonical validation plus Final certification prevents a wrong picture; byte identity remains a deterministic-mode property.
- Unconditional bignum orbit generation below `q=14`: removing it produces exactly the same shallow pixels because no shader invocation reads the orbit; only arrival time changes.
- Cross-machine-identical credit decay/admission timing: moving it to GPU `f32` would change when an orbit starts, not which Final pixel appears, but integer CPU safety is cheaper and avoids hangs, so fast mode loosens policy rather than moving it.
- Two-word, two-ulp `D` versus `D+16` agreement remains a Final/Measure check because both stored coordinate words feed the recurrence; PictureFast Preview does not pay for the second orbit.
- Reference residual words are discarded only after the production-shaped fixture found zero consumed-word changes in 40,928 bounded coordinates; the shader consumes the resulting `(re,im)` record with the merge-base multiply.
- Exact retained-shift `f64`, fixed zoom-14 switch, and `f64` scale mantissa: GPU `f32` would look unchanged while the shift and scale stay within 0.25 pixel and the exponent remains an exact integer; only the threshold needs to move if that oracle fails for the current extent and centre magnitude.
- Deterministic draft dimensions/order beyond exact buffer bounds: GPU/device-selected `f32` quality heuristics would alter transient blockiness and arrival time only; Final remains exact in extent and contract.
- Bit-exact CPU mirrors during ordinary rendering: a GPU-only implementation is already what produces the picture; the lab looks identical and loses only an always-on replay oracle, which remains available in conformance mode.
- Exact shallow smooth words and the current `1e-4`/`2e-3` tolerances: GPU `f32` remains the displayed result, and relaxing the oracle only up to `0.03565` smooth iteration cannot change a normalized channel by more than one code.
- Binary64 flat-warp inverse at a `1e-9` algebraic oracle: direct GPU `f32` looks the same while its source error remains below 0.25 pixel; exact inverse residual is invisible.
- Binary64 tumbled solve and exact `1e-12` pivot threshold: GPU or CPU `f32` would be hidden beneath the model's measured multi-pixel approximation except near a rejected pole; residual/pixel checks are the correct guard.
- Exact `f32` packing words for the homography: ordinary GPU `f32` conversion looks the same while the uploaded mapping stays within 0.25 source pixel; word identity adds nothing to that oracle.
- The 9x9x5 error corpus on every warp: it is an admission bound, so omitting it can display unbounded pole-crossing motion; run it for every precision and validation mode.
- Drift oracle and Gram-Schmidt every 64 steps: GPU `f32` makes no difference because production consumes neither result; this is test support, not pipeline architecture.
- Exact animated view coefficients: GPU `f32` may shift animation phase by a subpixel and otherwise looks the same; recorded angle/time is the deterministic replay mechanism.
- Exact palette and height CPU results: GPU `f32` is already authoritative for the picture; CPU values are test oracles only.
- Exact rebase-count agreement and record count words: GPU `f32` may take a different safe rebase and report a different integer count while producing the same colour; flags, bounds, and terminal category remain exact so a glitch cannot be hidden.
- Cross-machine-identical lighting, rasterization, filtering, and surface conversion: simply using GPU `f32` is the current lab; visible one-code agreement and categorical debug colours are the useful specification.

## Why the deterministic path remains valuable

`PrecisionMode::Deterministic` should remain a first-class, explicitly labelled path. Canonical centre bytes, fixed precision rounding, exact operation-order mirrors, stable planner records, and recorded generations make a replay explainable and let a future multiplayer arena decide whether two machines refer to the same slice. The CPU mirrors are especially valuable as offline differential oracles: they isolate shader/control-flow regressions without making every ordinary frame pay for duplicate calculation. The deterministic path is also the reference image for `PictureFast` tests and the escalation fallback when a Final error bound fails. Those are concrete uses; they do not imply that deterministic arithmetic belongs on the default interactive critical path.
