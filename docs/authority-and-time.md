# Authority and Time

Authority is a calculation, not a resemblance. One server owns the game history; clients estimate that history so input can feel immediate, then accept correction when the estimate and the calculation differ. The useful contract is therefore bounded convergence to server state, not equality between executions.

Authority is also independent of processing frequency. Inputs and outcomes belong to timestamps on one history. A server may wake, batch, integrate, substep, and broadcast on schedules chosen for load and numerical stability, but none of those schedules gives an event its meaning. Presentation is the sole exception because a display must be fed at its refresh cadence.

## 1. Authority Is the Server's Calculation

### 1.1 One writer of truth

Each game has one authoritative server for a running game. `pong-server` keeps connections, lobbies, and running simulations on one hub thread, calls the shared `pong_core::shooter::Sim`, and emits the resulting state (`crates/pong-server/src/lib.rs:368-450`). `fire-server` likewise gives one hub thread every lobby, runs `fire_core::sim::Race`, and states the essential division directly: clients send intents, never positions (`crates/fire-server/src/lib.rs:1-11`, `crates/fire-server/src/lib.rs:348-417`). The single writer is valuable because it leaves exactly one place where an ambiguous fact must become unambiguous; a cluster may later implement that logical role, but it must still expose one ordered authority per game.

The shared-core crates do not create shared authority. They create shared rules and a good predictor. Both the Pong client and server depend on `pong-core`, and both the Fire client and server depend on `fire-core` (`crates/pong/Cargo.toml:14-17`, `crates/pong-server/Cargo.toml:6-8`, `crates/fire/Cargo.toml:14-17`, `crates/fire-server/Cargo.toml:6-8`). `pong-core` deliberately has no engine or platform dependency (`crates/pong-core/src/lib.rs:6-12`), while `fire-server` and the Fire client both instantiate the same race model (`crates/fire-server/src/lib.rs:25-31`, `crates/fire/src/online.rs:25-29`). Reusing code lowers prediction error and makes rules easier to review; it does not turn a client execution into a vote.

The client's simulation is a predictor. Its output is provisional by construction, including when it runs the same source with the same inputs. Fire's online client already states the right reason: predicted car arithmetic may drift in its last bits, the car is corrected against server state, and the local position never decides an outcome (`crates/fire/src/online.rs:1-17`). On every authoritative state it replaces the local car fields, discards acknowledged inputs, and reapplies the pending suffix (`crates/fire/src/online.rs:224-260`). The arena client performs the same kind of rebase and replay for movement (`crates/pong/src/online.rs:918-990`). These are examples of eventual consistency in game networking: the server is authoritative throughout; the client is not a competing replica awaiting consensus.

### 1.2 A hit exists only on the server

A hit exists when, and only when, the authoritative server evaluates the interaction and commits its outcome. A client may immediately draw recoil, a tracer, or a predicted response, but those are presentation claims until authority reports what happened. The arena makes this boundary unusually clear. `pong-server` supplies accepted inputs to `Sim::step` and broadcasts the resulting bullets and player state (`crates/pong-server/src/lib.rs:409-507`); the shared simulation creates bullets, sweeps them against rewound bodies, resolves shields and head zones, and records damage inside that step (`crates/pong-core/src/shooter.rs:711-714`, `crates/pong-core/src/shooter.rs:784-831`, `crates/pong-core/src/shooter.rs:945-1106`). The client receives bullet heights from the server instead of reconstructing their paths, then derives its hitmarker from authoritative bullet disappearance and health loss (`crates/pong/src/online.rs:818-847`, `crates/pong/src/online.rs:909-919`).

The hit volume is an authority contract, not a renderer convenience. Its standing and crouched heights are tied to the silhouette the client actually draws, and the constants live in `pong-core` because both sides must agree where the body is (`crates/pong-core/src/shooter.rs:65-104`). The finite cylinder and head boundary are defined beside the authoritative hit test (`crates/pong-core/src/shooter.rs:112-130`), and the sweep uses those stance-dependent bounds for the final body and head decision (`crates/pong-core/src/shooter.rs:962-1030`). This model-aligned work matters precisely because authority must answer the question the picture invites: a player who aims at visible body geometry must not be judged against an unrelated hidden volume.

Server-only adjudication makes target-native floating point safe where replay equality would make it suspect. The bullet sweep uses transcendental and approximate arithmetic, but no client-calculated bullet can damage anyone; the repository records that boundary explicitly (`CLAUDE.md:15`, `crates/pong-core/src/shooter.rs:1064-1067`, `crates/pong-core/src/shooter.rs:1118-1123`). SIMD, fused multiply-add, target math libraries, and fast approximate math are therefore admissible on authority and prediction paths when they preserve the exact decisions and quantified budgets below. A faster calculation does not weaken authority; an ambiguous decision predicate does.

### 1.3 The determinism that survives

Consistency-determinism survives. For a fixed accepted event set, the authoritative server must have a well-defined order, exact decision rules at ownership boundaries, stable identities, seeded world selection, and enough recorded state to reproduce its own adjudication. Seeded generation still selects the world; a rewind still restores the same accepted events; an equal-time tie still has one result; an input sanitizer still has exact acceptance conditions. These properties make authority fair, auditable, and locally reproducible without constraining another machine's continuous trajectory.

Equality-determinism is dropped. The architecture does not require identical floating-point intermediates or state bits across native and wasm, scalar and SIMD, builds, targets, optimization levels, or contraction policies. It does not ban FMA, pin a software transcendental, preserve one expression tree for its rounding, or compare cross-target full-state hashes. Input-only bit-exact replay may be built as a separately costed product profile, but it is not a hidden prerequisite of ordinary authority.

The distinction prevents two common category errors. Seeded randomness is not a demand for equal floating trajectories: it is a demand that the same stable identity selects the same discrete choice. A fixed update order is not a demand for one universal instruction stream: it is a demand that the server's adjudication cannot change with hash-map traversal, packet arrival, or worker scheduling. The former governs what fact is selected; the latter governs how continuous estimates approach it.

### 1.4 What the player is promised

“Eventual” has a deadline. On receipt of an authoritative position correction, the predictor first restores the timestamped server state and reapplies only still-pending inputs. The displayed error then obeys a monotone envelope: it may not grow because of the correction, it is at most half the initial error after 50 ms, at most the greater of 10 percent of the initial error or 0.02 world metres after 120 ms, and at most 0.02 metres after 200 ms. A wrong discrete state, a path that would cross authoritative collision geometry, or an initial position error above 0.50 metres snaps on the next presentation opportunity instead of being disguised by smoothing.

Those numbers are engineering defaults, not measurements. They make the promise testable while leaving a title free to publish a stricter or looser supported envelope before testing. The default balances a short visual blend against the requirement that prediction cannot remain visibly wrong for several interactions; the 0.50 metre snap threshold is below the arena's standing hit diameter, so smoothing cannot preserve a body-sized lie. Orientation, velocity, and title-specific phase values require corresponding declared envelopes before they can gate a release.

Hit reporting has two clocks. The default server-work budget is p95 at or below 4 ms and p99 at or below 8 ms from the close of the eligible reorder cohort through adjudication, revision, and outbound enqueue. The default first-report budget at the client is p95 no worse than the measured round-trip p95 plus 25 ms and p99 no worse than measured round-trip p99 plus 50 ms, measured end to end from the timestamped trigger sample. These are defaults rather than benchmark claims; a release must measure them in each supported network envelope. A first report may be revised while its timestamp remains inside the rewind horizon, but every revision is an explicit correction and finality is bounded by that horizon rather than left implicit.

## 2. Authority Is Frequency-Free

### 2.1 Timestamped history

The server's monotonic session timeline is the time authority. Wire inputs carry a client input sequence, an event identity, and the client's estimate of the sample's server timestamp; authoritative state carries the server timestamp at which it is true, an increasing authoritative event sequence, a history revision, and the latest accepted input sequence for each relevant actor. Timestamps are integer durations in a declared epoch and scale. Their precision describes representation, never a processing period.

Clients estimate an affine mapping from their local monotonic clock to the server timeline through timestamp exchanges and retain offset, skew, round-trip time, and uncertainty. The server validates a claimed time against that exchange history, receipt time, sequence progression, and the rewind horizon. A future claim cannot gain future authority, a causally regressing claim cannot gain extra rewind, and an implausibly old claim receives no historical credit. Client time is evidence constrained by server observations, not authority smuggled onto the wire.

Every accepted event receives an effective server timestamp. Movement intent changes take effect there; trigger edges, boosts, jumps, melee, joins, and other semantic transitions occur there; cooldowns and lifetimes are durations from timestamps rather than counts of updates. An implementation may integrate between event times using any stable method that meets its gates. It may also choose a uniform internal step, but the step number cannot enter a message, an event identity, a gameplay rule, or an acceptance condition.

### 2.2 Bounded reordering and simultaneity

Arrival order is network noise, so it cannot be a gameplay tiebreaker. The server holds accepted events for a bounded reorder window, closes a cohort when its watermark passes, and adjudicates that closed event set in timestamp order. The default reorder window is 12 ms. This is an engineering default, not a measured jitter percentile: it is short enough to fit inside the 25 ms first-report allowance while giving ordinary packet reordering a chance to stop influencing outcomes. A title changes it only together with its latency and fairness gates.

Events with the same representable timestamp are simultaneous wherever the rule can be commutative. Each independent attack reads the same pre-cohort authoritative state, all valid outcomes are collected, and their effects are combined as sets or associative reductions; one attack does not erase another merely because its packet was dequeued first. If a resource can have only one owner or another commit is inherently noncommutative, the stable tie key is `(event_class, actor_identity, input_sequence)`.

Each tie component earns its position. `event_class` comes first because semantic dependency is a rule of the game rather than a privilege a sender can race for: a class table can state, for example, whether a membership transition makes an action invalid before interaction outcomes commit. It is versioned and server-owned. `actor_identity` comes next because a stable session identity removes traversal and arrival bias among different actors; any fairness policy that rotates priority must derive that rotation from an earlier authoritative event, not receive order. `input_sequence` comes last because it orders repeated events from one actor and makes their identities unique without allowing a later packet to precede an earlier one at an equal timestamp. The complete order is effective timestamp followed by that key; batch size, thread, connection, and packet arrival are absent.

The commutative rule and tie key serve different cases. Commutative adjudication preserves genuine simultaneity, such as two otherwise valid lethal shots. The key resolves only the irreducible remainder, such as two simultaneous acquisitions of one exclusive object. Sequentially applying the key to every interaction would turn a deterministic implementation detail into a gameplay advantage, while pretending every rule commutes would leave exclusive ownership undefined.

### 2.3 Event-keyed randomness

World generation remains keyed by immutable world identity and a session seed. Runtime authoritative randomness is keyed by event identity rather than a mutable stream: `(session_seed, subsystem_domain, event_class, actor_or_source_identity, input_sequence, draw_purpose, draw_index)`. Every component is accepted event data or a versioned domain constant. A retry or rewind of the same event therefore selects the same choice even when batching, substeps, worker assignment, or arrival order changes.

Tick number, packet order, worker index, presentation sequence, and internal substep are forbidden random inputs. A subsystem that needs several values gives each a stable purpose and index; it does not advance a global generator whose later values depend on which branch happened to draw first. This preserves the reason for the repository's seeded-RNG rule while removing its tick-indexed prescription (`CLAUDE.md:14`). The existing arena generators demonstrate why shared seed identity matters (`crates/pong-core/src/shooter.rs:288-315`, `crates/pong-core/src/shooter.rs:370-405`); §5 narrows how their shared world decisions must eventually be represented.

### 2.4 Rewind and revision

Late but admissible evidence may revise recent authority. The server keeps timestamped checkpoints and accepted events for a bounded rewind window, restores the latest checkpoint no later than the event, advances to the exact event time, adjudicates it, and replays later accepted events in the stable order. The default rewind depth is 300 ms, expressed as a duration. This default is grounded in the arena's existing product scale of eighteen 60 Hz history steps (`crates/pong-core/src/shooter.rs:194-197`) without retaining those steps as the contract.

When re-adjudication changes a previously emitted state or outcome, the server increments the history revision and sends a correction naming the affected authoritative sequence interval. Old messages remain forensic records of an earlier revision but cease to describe current authority. Evidence older than the rewind horizon is final and cannot silently rewrite history; invalid, future, or over-age timing receives no rewind credit and is handled by the title's explicit current-time or rejection rule.

The server may checkpoint, integrate, and replay at internal boundaries chosen for numerical stability. Fast projectiles, contacts, stiff constraints, and long intervals often justify bounded substeps or fixed solver iterations. Such choices may be pinned within a server release when needed to reproduce its own adjudication, yet remain unobservable implementation law rather than wire frequency. A change is safe when exact verdicts remain stable, continuous state stays inside declared tolerance, and the recorded authority remains interpretable.

## 3. The Clock Lives at Presentation

Exactly one pipeline stage may promise a frequency: the stage that faces the display. The adopted rendering policy puts scene output in offscreen `SceneFrame` color and depth, forbids the scene renderer from touching the swapchain, and makes a cheap warp pass present the newest finished scene every display frame (`docs/atw-first-rendering.md:3-8`, `docs/atw-first-rendering.md:73-86`). The presenter architecture makes that ownership structural: `presenter.rs` owns the surface and its entry point consumes a finished scene plus a newer view pose (`docs/presenter-architecture.md:13-22`, `docs/presenter-architecture.md:71-81`).

Presentation samples a timeline; it does not advance authority. The scene may render variably and offscreen, while the presenter reprojects and paces the newest complete image at rAF or the native display opportunity. A 60 Hz, 120 Hz, or adaptive-refresh promise belongs here because failure to meet it is a pacing failure visible at the display. The late input read, presenter-side UI, independent scene resolution, and ATW invariants survive unchanged (`docs/atw-first-rendering.md:90-122`, `docs/presenter-architecture.md:62-67`).

Snapshot broadcast cadence is a bandwidth and quality-of-service knob. Sending every current server step is merely today's implementation in `ember-server` (`crates/ember-server/src/lib.rs:336-357`); the arena and racer currently gate state on `STATE_EVERY_TICKS` (`crates/pong-server/src/lib.rs:448-507`, `crates/fire-server/src/lib.rs:447-461`). Under this law a broadcaster may adapt to queue pressure, loss, observer interest, or state change. Each snapshot remains true at its source timestamp and revision, so changing broadcast rate changes freshness and bandwidth, never which event the server accepted or what happened.

Client input sampling is also local scheduling. A device callback may sample more often than prediction, a client may coalesce held intent, and an edge may be sent immediately; the sample retains its timestamp and sequence. Prediction stepping is equally local. Fire may keep its current fixed-step accumulator because it reduces reconciliation error (`crates/fire/src/online.rs:134-160`, `crates/fire/src/online_game.rs:191-202`), and another client may use variable or adaptive integration. Neither schedule binds the authority, and neither appears as a promised frequency on the wire.

The boundary is absolute: gameplay duration, event order, rewind, random choice, snapshot identity, and authority never count presenter frames; presentation never authors a server event from its frame-relative late pose. The input-latch design already protects the latter half by forbidding the cosmetic view read from reaching anything sent, stored, or ticked (`docs/input-latch.md:106-112`). The result is one clocked consumer of time and a frequency-free history upstream of it.
